A good score in a paper is not yet a working product. This page covers what you must do to deploy such a system, and what the paper does **not** show.

## 10.1 Recalibrate the threshold whenever the gate changes

A threshold is tied to one model. If you swap the gate model and keep $t$, the false-alarm rate changes by an amount and in a direction that headline scores do not predict.

- The threshold that gives a **2% false-alarm budget** differs by more than **3×** across the six deployment candidates (from 0.205 to 0.725, which is 3.5×).
- In the worst case, Gemma-3-270M loses **28.0 F1 points** when run at another model's operating point.

**Rule:** calibrate the threshold per model, on held-out data.

## 10.2 Choose by calibration if the threshold will adapt

A system that learns its threshold from user feedback uses the gate's **probabilities**, not only its ranking. The best-ranking gate was the worst calibrated (ECE 0.3036 against 0.0425 for the best-calibrated one). So choose on calibration, or calibrate after training and measure again.

## 10.3 Choose the false-alarm budget on purpose

At the deployed point the system emits **3,682 hints**, and **23.5%** of them fall where the corpus says it should have been silent. A tighter budget gives fewer wrong interruptions but also fewer right hints (end-to-end precision up, end-to-end exact match down). Which trade is right depends on how much an interruption costs your user.

## 10.4 Memory cost

One 4-bit 1B base with two adapters and the head used **1.05 GB**. A second adapter costs **42 MB**, where a second base costs **957 MB**. This is a saving of **915 MB**. The unified model needs one adapter, so 1.05 GB is an upper bound.

## 10.5 Cost on a CPU

We timed both final checkpoints on a **4-core cloud CPU**, batch size one, in ONNX Runtime with NF4 weights (the format used in training).

| Measure | $k = 6$ | $k = 10$ |
|---|---|---|
| Gate time per marker | 1,793 ms | 2,909 ms |
| Extra time for a triggered hint | 7.79 s | 5.01 s |
| Early-exit saving, ONNX Runtime NF4 | 2.86× | 1.51× |
| Early-exit saving, PyTorch eager | 1.75× | 1.35× |
| Ideal saving $16/k$ | 2.67× | 1.60× |

![CPU savings](/attachments/notes/proactive-assistant/fig18-cpu-savings.png)
*Figure 21. Measured speed-up of the gate from early exit, compared with the ideal $16/k$. [PDF](/attachments/notes/proactive-assistant/fig18-cpu-savings.pdf)*

- ONNX Runtime delivers a saving close to the ideal $L/k$ of [[notes/proactive-assistant/5-early-exit-and-unified-decoder|the cost formula]].
- **4-bit weights do not speed up** the gate at batch size one (1,793 ms against 1,611 ms in fp32). They save **memory** (1.65 GB against 4.99 GB).
- Half precision (bf16, fp16) is **slower** here, because these CPUs lack the instructions that make it fast.
- The NF4 variant reproduces the GPU model: gate probabilities correlate at $r = 0.998$ ($k=6$) and $0.991$ ($k=10$), decisions agree on 100.0% and 96.7% of sampled markers.
- Timings come from a **cloud container**, not a phone or glasses. No consumer device was measured.

**Words used here.**

- **ONNX Runtime.** A program that runs a model saved in the ONNX format. It is tuned for fast inference, often faster than plain PyTorch on a CPU.
- **PyTorch eager mode.** Running the model step by step in PyTorch without special compilation. Each call has overhead that does not shrink when fewer layers run.
- **Latency.** The time from input to output for one request, here milliseconds per marker.
- **Cache.** Saved intermediate results that are reused. **Prefix caching** reuses the computation for a prompt beginning that does not change.
- **Cloud container.** A rented virtual machine. Its exact CPU is hidden, so timings also depend on which host you get.

## 10.6 Limits of the paper

- One main corpus whose dialogues and labels were **generated by a language model**.
- Most configurations were trained **once**, so confidence intervals are sampling intervals over fixed models. Differences below the noise floor are not resolved.
- **Training budgets differ** (2 epochs vs 4 epochs).
- A second-family unified model, more epochs, and other exit depths were not run.
- The human study has **1,144 ratings**, mostly from **one rater**.
- The cascade's cost with **prefix caching** was not measured, so combined-optimization numbers are only an upper bound.
- The system is tested on **transcripts**, so speech-recognition errors are absent from every number.

## 10.7 Ethics

- The system **listens all the time** to a conversation for one wearer, with people nearby who did not consent and cannot see the profile.
- The profile is **persistent personal data** and a target for compromise.
- A **false alarm** interrupts everyone present, so bystanders also bear the cost of errors.
- Non-user consent, disclosure norms and a retention policy are deployment requirements that this work **does not address**.
- The ICSI meeting participants agreed to research recordings, not to a study centred on one participant. We use the corpus only as released and under its own licence.

## 10.8 Data and code

We release the construction and validation code and every artifact the paper's numbers come from: the canonical marker index, per-marker gate predictions, generation outputs, all judge prompts and raw judgments, scripts, and run manifests. The derived corpus is not redistributed because its three upstream sources have different licences. The pipeline rebuilds it from those sources.
